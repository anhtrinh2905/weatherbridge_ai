# Data boundary

Large or sensitive data does not belong in Git. Keep manifests, schemas, small
synthetic samples, checksums, and provenance records only. Store raw data,
processed datasets, model weights, and reports in approved external storage.

## Disaster and weather training data

- `catalogs/dien_bien_disaster_inventory_v1.json` is the canonical, versioned
  seed inventory. The CSV files beside it are generated views for inspection
  and simple offline joins.
- `processed/training/` is generated by `make training-csv` after database
  backfill. It contains normalized forecast, observation, event, location, and
  ingestion-manifest CSV files. This directory is intentionally ignored by Git.
- `processed/training/manifest.json` records row counts, file sizes, CRS, source
  products, schema version, and current quality status for each generated export.
- Village rows with `coordinate_confidence=unresolved` are labels from public
  reports without a defensible point coordinate. Never substitute synthetic
  household coordinates for them.
- `catalogs/muong_pon_villages_v1.json` lists **22** bản for xã Mường Pồn
  (post-merger). Coordinates are intentionally `unresolved` until a cited GPS/GIS
  source exists — never invent centroids for map markers.
- Join CSV tables using UUID columns. Use `location_id + valid_time_utc` to
  compare forecast rows with observations, and preserve `lead_hours` as a model
  feature.
- `processed/training/training_samples.csv` is the ready-to-use hourly feature
  and target view. It joins each forecast lead with the best-match observation
  at the same location and valid time. Disaster labels remain separate because
  unresolved village coordinates must not be promoted to exact point labels.
